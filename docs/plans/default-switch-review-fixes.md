## 2. 必须保持的不变量

- Pi 仅改默认仍走 `/api/providers/set-default`，只改 `settings.json` 的 `defaultProvider` / `defaultModel`；`models.json`、`auth.json` 字节不变。
- Codex 的已存供应商切换仍走 `/api/codex/activate`；Claude 行菜单仍走 `/api/claude/activate`，不重新提交供应商表单。
- 真实内容编辑仍正常保存。保存既有供应商仍支持三个步骤；新建和复制保留原三步流程。
- `piDirty` / `draftSignature` 继续表示未保存的用户意图，供离开保护和 `beforeunload` 使用。不能为了禁用按钮而把真实修改伪装成未修改。
- 每次写入仍使用对应目标的 revision（配置修订标识，用于拒绝过期写入）；409 不得改动外部文件。开始新写入时清除旧 conflict 标记。
- 既有凭据不回到浏览器；`bridge.models` 省略保留、显式 `{}` 清空的修复不得回退。
- 成功反馈只在请求实际成功后显示。取消请求或关页面不等于撤销服务器已完成的写入。

### A. 统一 Pi 各步骤的可保存判定

**入口**：`src/App.jsx` 的 `save`、`savePiChanges`、`ProtocolStep`、`CredentialsStep`、`ModelsStep`；`src/ui-kit.jsx` 的 `StepFooter`；必要时使用 `src/model-draft.mjs` 的小型纯函数。

**已复现**：非默认、已有两个模型的供应商只改默认单选，第 3 步禁用「保存更改」，退回第 2 步却重新可用。点击后发出 `/api/providers`：默认没有变化，模型文件被重写，夹具的 `thinkingLevelMap` 从 `{low:"minimal", high:"high", xhigh:"xhigh"}` 变成 `{xhigh:"xhigh"}`。

**实现要求**：

1. 分开表达两个事实：
   - `dirty`：草稿是否有未保存修改，包括默认单选。
   - `canSaveChanges`（名称可调整）：这个「保存更改」动作是否有能写入的修改。
2. 对从磁盘打开的供应商：当前 Pi 默认可以保存单选变更；非默认供应商的普通保存必须有内容变更，即 `piContentDirty`。是否来自磁盘以 `identity.sourceId` 为准，不能误伤新建、复制或重名覆盖流程。
3. 三个步骤共用这条判定。若扩展 `StepFooter`，新增能力参数默认维持旧行为，不改变 Codex/Claude 的保存语义。不要简单把显示用 `dirty` 换成 `contentDirty`，导致页脚声称「没有改动」。单选-only 时仍需诚实说明应到第 3 步「设为默认」。
4. 在共同的 `save(false)` 入口也检查，而不只禁用第 1/2 步按钮：第 3 步会直接调用它。没有可写内容时不发请求，必要时给出已有风格的提示。
5. 当前默认供应商仅换模型时，仍走默认专用接口；地址、模型容量、兼容项等真实内容变更仍走供应商保存。不要借机修改所有正常供应商保存的模型规范化逻辑。

**验收**：

- [x] 非默认、两模型夹具，仅改单选：第 1、2、3 步普通保存均不可执行；没有 POST，三个 Pi 文件均不变。
- [x] 单选变更仍使离开提示和 `beforeunload` 生效；不能靠清掉 dirty 通过测试。
- [x] 第 3 步「设为默认」仍可执行，选中的第二个模型实际成为默认；请求仅为 `/api/providers/set-default`，模型和认证文件字节不变。
- [x] 当前默认供应商只改单选，可从第 1/2 步保存，同样只写默认字段。
- [x] 加一个真实内容修改后，三个步骤的普通保存恢复正常；非默认供应商不会因此抢走全局默认。
- [x] 新建、复制、改名流程无回归。

测试放入 `tests/model-draft.test.mjs`（如提取纯判定）及 `tests/model-deletion-ui.test.mjs`。夹具包含手写 `thinkingLevelMap` 和未识别字段；必须查请求路径和磁盘字节，不能只查按钮文案。

### B. 补齐 Codex 成功页的失败反馈

**入口**：`src/App.jsx` 的 `activateCodex`、`CodexSuccessScreen` 调用点；`src/codex-view.jsx` 的 `CodexSuccessScreen`。

**已复现**：停在上一次成功页，用侧栏切换到缺凭据的供应商，400 完全无提示；外部文件改动造成 409 时，只有短暂 toast，没有持久横幅和重新读取入口。

**实现要求**：

1. 把共享 `error` / `conflict` 传给 `CodexSuccessScreen`，通过已有 `ErrorBanner` 渲染，不另造一套错误组件或 toast-only 分支。
2. 失败保留上一次真实结果，不伪造新的切换成功；新的错误必须可见并能滚入视口。
3. 下一次写入开始清除旧 conflict；失败类型从 409 变成 400 后，不能遗留横幅的重新读取按钮。

**验收**：

- [x] 真实服务器返回 400：成功页内出现持久错误，目标未切换，文件不变。
- [x] 在浏览器读取后实际修改隔离目录的 `config.toml`，再从成功页切换：返回 409，外部字节保留，横幅包含可操作的「重新读取」。
- [x] toast 到期后横幅和重新读取入口仍在；需实际等待到期或受控推进时钟。
- [x] 随后一次非冲突失败不带旧 conflict 按钮；成功重试更新成功结果并清除错误。
- [x] 明暗主题和窄屏下横幅及按钮可见，无新增布局溢出。

用真实 API 制造 400/409，不把所有失败都替换成前端 mock。新增用例进入现有生产浏览器套件。

### C. 阻止在途保存/切换覆盖后续草稿

**入口**：`src/App.jsx` 的保存/激活生命周期、`guardLeave`、侧栏和工作区交互、toast action、`beforeunload`；`src/claude-view.jsx` 的对应已有保存/激活入口；必要时小幅调整共享组件。

**已复现**：暂缓交付一次真实 Codex 激活响应，等待期间打开另一供应商并改模型 ID。确认新草稿已触发 `beforeunload` 后释放响应，`loadCodexForm` 和 `setView("success")` 无条件执行，草稿与离开保护消失。Pi `applyPiDefault` 有同类无条件覆盖路径。

**采用决策：短暂交互锁，而不是异步结果归属框架。** 本地保存期间暂不允许编辑或离开，成功/失败后解锁。同步引用从入口保护重入；可见锁在校验通过、开始请求后开启，避免禁用校验失败时需要聚焦的字段。这样避免引入导航代次、跨页面缓存、迟到结果合并等更大改造。

**实现要求**：

1. 为供应商保存/激活建立单一、可复用的在途状态：包含能同步拒绝重复入口的引用标记，以及驱动界面的状态。只靠 React 下一次渲染后的 `saving` 不足以挡住同一时刻的两次调用。
2. 覆盖本次 Pi 默认切换、Codex 激活、Claude 行菜单激活，以及三个目标已有的供应商保存入口。复用小型生命周期保护，不重构后端事务或把整个应用改成通用请求框架。
3. 在途时禁止会写草稿、丢草稿或启动竞争写入的交互：
   - 供应商/目标切换，添加、复制、删除和批量动作；Settings/Prompts 导航。
   - 当前表单字段、默认单选、步骤跳转、JSON/批量编辑、成功页返回/添加等入口。
   - 工作区外的 toast action，特别是撤销、弃稿后导航和重新读取，不能成为绕过点。
4. 显示现有风格的忙碌状态，保留内容阅读和滚动；不隐藏主导航、不更改色板和密度。采用真实控件禁用/只读及必要的入口检查，不能只用 `pointer-events` 或降低透明度假装锁住。键盘入口也要检查同一个事实。
5. `useDialog` 继续用 `locked` 控制取消/Escape；对话框外的锁不能让忙碌提示或请求结束后的错误失去可访问性。
6. 成功、400、409、网络失败及异常均通过 `finally` 解锁；验证未通过时不要遗留锁。每次操作只能发起一笔写入，不得出现第一笔完成就把第二笔解锁的情况。
7. `beforeunload` 在有供应商写入待完成时也应提醒，不能因为发起时草稿未编辑就允许无提示刷新。用户坚持关闭后不承诺撤销服务器写入。
8. 解锁后不重放等待期间被阻止的点击或旧回调；不要把它们排队应用到新草稿。

**测试注意**：审查用临时实验允许“等待时继续编辑”，是为证明旧代码会丢数据。采用本方案的交互锁后，应改为断言这些操作被可靠阻止，不能机械要求旧实验中的输入仍可成功。测试的最终契约是“不发生未确认的草稿丢失”，不是强制使用某种内部机制。

**验收**：

- [x] 用 CDP（Chrome DevTools Protocol，浏览器调试协议）暂停真实响应的交付，或在测试浏览器中受控延迟已取得的真实响应；不能只靠固定 sleep 碰概率。
- [x] Pi 与 Codex 均在请求暂停期间尝试侧栏切换、目标切换、编辑当前模型、第二次写入及 toast action；页面/草稿不被改变，写请求总数仍为 1。
- [x] 除调用处理器的检查，还用真实鼠标/键盘输入验证禁用。DOM 的 `.click()` 或直接改 input.value 与用户交互不等价，不能只测其中一种。
- [x] 释放成功响应后正确更新默认/生效标记，进入相应成功页，控件恢复可用；后续新输入可保留并触发离开保护。
- [x] 释放 400/409 或制造网络失败后不生成新的成功结果，也不强制跳页；原草稿不变，错误可见且可重试，锁确已释放。若起点本来就是成功页，按 B 保留上一笔真实结果并显示本次错误。
- [x] Claude 新增侧栏入口同样不能在请求期间切走或触发竞争写入。只复用生命周期保护，不新增 Claude 第 3 步快捷激活语义。
- [x] 普通保存至少各有一个 Pi/Codex 延迟响应回归，证明不是只堵住新按钮而留下共用保存路径的同类洞。
- [x] 在途 `beforeunload` 提醒生效；完成后无未保存草稿时不残留提醒，有未保存草稿时仍保留提醒。

## 4. 验证方法和执行命令

### 每个切片的短反馈循环

1. 在 `tests/model-deletion-ui.test.mjs` 现有生产服务/CDP 测试组织中补用例。复用现有夹具/驱动，避免为四个缺陷新增一套长期浏览器框架。可以在测试中拦截浏览器请求，但不要给产品代码新增测试专用端点、全局变量或绕过开关。

3. 实现后重新构建，定向用例通过，再跑相关完整套件。测试函数名可使用一致前缀，便于 `--test-name-pattern` 定向执行。


## 5. 执行 agent 的最终交付格式

1. **完成**：逐项说明 A–D 的实际行为及关键实现选择，不只报文件数。
2. **验收证据**：新增回归的修复前失败/修复后通过；完整测试命令、退出码、数量与每个跳过原因；浏览器检查范围。
