## 0.3.6 - 2026-08-26

- A bundle older than the sources it was built from now blocks the restart instead of being applied. That is the state an interrupted upgrade leaves behind — a pull gives every changed file a current mtime, so between the pull and the build the source tree really is newer than `dist/client` — and restarting there puts a new server behind the previous page, which is the one outcome of a half-finished upgrade that looks like it worked. The button is disabled with the reason, and `POST /api/restart` returns `409` regardless of what the page thinks, because the page asking may be older than the rule. A `npm run build` clears it with no restart.
- The rule for that has one home. It was a test helper — the UI suite serves a gitignored `dist/client` that no checkout or pull ever updates — and is now `lib/built-ui.mjs`, read by both the suite and the server. It is asked only when this process is the one serving the UI: under Vite the question is meaningless, and a release archive carries no sources to be out of step with.
- The panel can find out that a newer release exists, and get it onto disk. `POST /api/update/check` reads this project's latest GitHub Release; a checkout is offered `git fetch` → `merge --ff-only` → `npm ci` only if the lockfile moved → `npm run build`, and an archive install is offered the platform's archive unpacked into a *sibling* directory. What it never does is rewrite the directory it is running out of, or restart on its own: the upgrade lands on disk, the card then has something to apply, and the restart stays a separate press with its own guarantees.
- Nothing reaches the network unless somebody pressed the button for it. There is no timer, no check on page load, and none at startup — the constraint `docs/compatibility.md` already made for the Pi update monitor now covers the manager's own check, and the panel names `api.github.com` before the request rather than after. GitHub's anonymous rate limit is reported as itself instead of as a generic failure.
- An upgrade that cannot be applied says which of the three reasons applies — not a git checkout, no upstream branch, or uncommitted changes — and names the files in the way. Nothing is stashed, merged or fetched on someone's behalf to get around it.
- A failed step stops the sequence and shows the last lines of its output. The build is last for a reason: a source tree newer than its bundle is the mismatch the test helper exists to catch, so a build that fails is never followed by an offer to restart.
- The compatibility card can apply an upgrade. It already said when the checkout had moved ahead of the process, and then left the reader to find a pid and kill it — which is the version of an instruction nobody carries out. `POST /api/restart` performs the handover, and the button reads "重启以应用 0.3.6" when there is something to apply and "重启本地服务" when there is not.
- The handover is ordered so that a bad upgrade cannot leave the machine with no manager. This process stops listening, starts its replacement from the files now on disk, and waits for a *different* process id to answer on the port before exiting. If the replacement exits instead — a half-written file, a broken upgrade — the old one takes the port back and puts the reason in `/api/state`, where the page that asked for the restart is already looking. A replacement that has exited is not waited out: its exit code is a better account than a timeout.
- The restart is confirmed only when the settings form has actually been edited. Confirming on the screen's `dirty` flag would have asked almost everyone to approve losing nothing: two of the five keys this screen owns are absent from a typical `settings.json`, which the footer reports as unwritten defaults, and a restart does not lose a key that was never there.
- The replacement inherits this process's output only when it is a file or a terminal. The launcher points it at a log file, which is where a startup failure has to land — but a pipe belongs to whoever spawned this process, and holding its write end open from a detached child leaves that reader waiting for an end that never comes. Found by hanging the UI suite for seven minutes rather than by reasoning about it.
- The PowerShell launcher's reuse report now has a local regression test, not only a CI job. It copies the launcher to a Windows-local path first, because that is not optional: the default `RemoteSigned` policy refuses an unsigned script on the UNC path a WSL checkout is reached by. The test skips where no Windows PowerShell is reachable.

## 0.3.5 - 2026-08-26

- The compatibility panel no longer reports the Pi and Codex versions that were installed when the manager started. Both were detected once at startup, so a manager left running across a `pi` upgrade — the launcher reuses an already-running instance, which is the normal way to reach it again — kept naming the release the machine no longer had, and the panel that exists to answer "which Pi is this talking to" was the one thing on screen that could not. They are now detected on demand through a self-refreshing cache in `lib/version-detect.mjs`. Nothing on the request path waits for the detection: the launcher decides whether a port belongs to this manager by probing `/api/state` with a one-second timeout, and detection can outlast that whenever it needs a login shell, so a reader gets what is already known and an aged answer is refreshed behind them. `lib/litellm-bridge.mjs` had already established both halves of this for the bridge binary; the versions beside it had not.
- The panel now says when the checkout has moved ahead of the process serving it. The manager's own version deliberately stays the one read at startup — it names the code actually running, and re-reading the manifest would claim an upgrade this process has never loaded — so after a `git pull` without a restart every number on the card is the old release, which reads as an upgrade that silently failed. `pendingAppVersion` carries what the manifest now says, and the card names both versions and the restart. The launcher already said this on the command line; the browser did not. Both the state payload and the rendered card are regression-tested, the latter by moving a copied checkout's manifest underneath a running server and reloading — mutation-checked by suppressing the field and watching the browser test fail.
- Version detection goes through a shell on Windows. Both tools are installed there as `.cmd` shims, which `execFile` cannot start on its own, so the panel reported `unknown` on a machine where the command answers perfectly from a prompt. Measured rather than reasoned about: on Windows 11 with Node 22 and Codex installed, `execFile("codex", ["--version"])` fails `ENOENT` without `shell` and returns `codex-cli 0.144.5` with it.
- The launcher no longer offers a restart as the way to pick up a newly installed LiteLLM. The bridge resolves that binary on every read precisely so an install made after the manager was opened is noticed without one. What a restart is actually for is what the process fixed at startup — its version and its two directories, which are the lines printed directly above.
- The PowerShell launcher reports a reused instance, as the bash one has since 0.3.2, and prints the URL and both directories unconditionally. It printed nothing at all when it opened a browser, which is the failure the bash launcher fixed by always printing: a blocked browser bridge left no port and no error on screen. Someone who moves between WSL and PowerShell reads the two as one command. Executed on PowerShell 7.6.3: a fresh start, then a second run that reported the running instance's version, both of its directories, and `Stop-Process -Id <pid>`.
- Documented that PowerShell cannot run this launcher from a WSL checkout, because the failure names everything except this project. The default `RemoteSigned` policy treats `\\wsl.localhost\...` as remote and refuses any unsigned script there with `is not digitally signed`, and `docs/usage.zh-CN.md` invited exactly that attempt by saying the two launchers are aligned. Both READMEs and the archive's `INSTALL.md` now say where the checkout has to live and point a WSL checkout at the bash launcher.
- The archive's install guide leads with `Unblock-File` rather than an execution-policy override. Clearing the download mark is the narrower fix; the guide previously offered only `-ExecutionPolicy Bypass`, without saying that it switches a security control off for the run rather than changing a setting.
- CI starts the Windows launcher twice and checks the reuse report, so the start-and-reuse path is executed on Windows rather than only parsed. Its first run already earned its place: the launcher behaved, and the check itself was wrong — it compared the printed config directory against the string it had passed, which on that runner is not the same text after Windows resolves it. It now asserts the directory it was given by leaf, and records the runner's `TEMP` in the log.
- Two more statements caught up with the project. `docs/architecture.md` credited `server.mjs` with version detection, which now lives in `lib/`, and described the launcher evidence as a PowerShell parse, which CI stopped being. `AGENTS.md`'s quick check ran six suites of nine; it runs `npm test`, for the same reason `CONTRIBUTING.md` was changed in 0.3.4.

## 0.3.3 - 2026-08-25

- Added `npm run install:launcher`, which takes no arguments and no destination path. The README's install step was a two-operand `install -m 700 <source> <destination>` command that only works from inside the checkout; run from anywhere else it fails with GNU install's own "missing destination file operand", a message that names neither this project nor the mistake.
- What it installs is a shim rather than a copy of the launcher, so the checkout is the only copy that exists. A copy stops matching the checkout at the next `git pull`, and a stale launcher does not fail: a pre-0.3.0 one starts, and silently stops handing the Codex directory and the LiteLLM path to the detached server, so the managed bridge breaks with nothing on screen connecting it to the launcher that caused it. It refuses to overwrite a file at that path that is not one of ours unless `--force` is passed, because that is a directory of the user's own scripts.
- The launcher now compares its own content with the checkout's copy and warns before starting when they differ. Content rather than a version string, so there is no second copy of the version to keep in step and a copy from any generation is caught.
- The launcher refuses a Node older than the floor declared in `package.json`, which now carries an `engines` field. The floor is read from the manifest rather than repeated in the launcher, under the same one-copy rule as the compatibility baseline; below it the failure being replaced is a syntax error from inside the server, which names neither Node nor its version.
- When the launcher cannot find a checkout it names all four places it looks and what each currently resolves to, plus both ways out. It used to print only the path it had settled on, which left the reader unable to tell which mechanism had chosen it and therefore which one to correct.
- Added `npm run setup`, which is install, build, and launcher in one command, so a fresh clone reaches a running manager without reading the README first. Verified from an actual fresh clone rather than from this checkout.
- The PowerShell launcher gained all three: the same four-place discovery message, the same manifest-declared Node floor, and the same stale-copy warning. Someone who moves between WSL and PowerShell reads the two as one command, and a Windows user could reach every one of those failures with no guidance at all.
- The Node floor is the lowest major any alternative in the range allows, so a manifest written `"^20 || ^18"` is not read as requiring 20.
- The PowerShell launcher reports the current directory without PowerShell's `Microsoft.PowerShell.Core\FileSystem::` provider prefix, which is what `(Get-Location).Path` returns on a UNC location — `\\wsl.localhost\<distro>\...`, exactly how a WSL checkout is reached from PowerShell. Verified on 7.6.3 that `Test-Path` and `Join-Path` accept the prefixed form, so this was presentation rather than behaviour.
- CI runs the Windows launcher instead of only parsing it. Both of its first-run refusals — a missing checkout and a Node below the floor — had never been executed by anything, because the bash launcher's equivalents live in `tests/launcher.test.mjs`, which cannot run PowerShell.

## 0.3.2 - 2026-08-25

- Fixed the bridge log being world-readable. It was opened with the default `0644` while every other file this manager writes is `0600`, and it is the one file here whose contents this project does not choose: it captures LiteLLM's own stdout and stderr, where a traceback or a debug line can carry the upstream key. Existing logs are chmodded on the next append, because a mode passed at creation does nothing to a file that already exists.
- Fixed a URL saved into the bridge's key slot being accepted in silence. Versions before 0.3.0 could write the upstream address there, and nothing downstream could tell: the proxy started, authenticated with an address, and the upstream answered 401 far from the cause. A submitted URL is now refused where the mistake is still attributable, and a stored one reads as no credential so the form asks for a real key. The stored value is not erased on sight — only an explicit save replaces it.
- The bridge form no longer offers to reuse a key that cannot be used. Its placeholder said "留空表示沿用已保存的 key" whenever a bridge existed, including for the legacy bad data above, where there is nothing to reuse and leaving the field blank is refused. It now keys off whether a usable credential is actually stored, and says plainly what happened when one is not.
- Fixed the launcher test leaking two background servers on every run. It looked for the process with `pgrep -f PI_PROVIDER_MANAGER_PORT=...`, but the launcher passes the port through the environment and `pgrep -f` searches the command line only, so cleanup silently matched nothing. It now reads `/proc/<pid>/environ`, with a `ps -E` fallback where there is no procfs — that fallback is unverified, since this repo is developed on WSL2.
- The UI tests refuse to run against a stale `dist/client`. The bundle is gitignored, so `git pull` never refreshes it and the tests, which serve the built output, fail on selectors unrelated to any real defect. `tests/helpers/built-ui.mjs` compares the bundle's timestamp against `src`, `index.html`, and `vite.config.mjs`; `package.json` is deliberately excluded, because a version bump does not change the bundle and a guard that cries wolf is one people learn to ignore.
- Every piece of text now meets WCAG AA contrast in both themes, and it is measured rather than asserted. `design-qa.md` had recorded "Colors and visual tokens: passed" for two releases on inspection alone while 17 of 64 light-theme elements sat below AA — both primary buttons among them at 3.05:1. White text now sits on a new `--orange-strong` rather than on the brand `--orange`, so borders, rings, and badge tints keep the brand value.
- The contrast audit also covers the states a resting page never shows: the toast, the delete dialog, the error banner, and every hover state the stylesheet defines, with the pointer moved for real. `.safe-default` only exists while its row is hovered and sat at 4.49:1 on the default row's tint until that sweep found it, hence `--blue` is now `#2b66d8`. Inherited opacity is composited too, so a faded control is measured as it is painted.
- Target sizes are measured against WCAG 2.2 SC 2.5.8. The tip dismiss button went from 22px to 24px, and `.safe-default` grew from a 16px line of text to a 24px target — downward, into padding the row already had, so no text moves and the row height the layout tests pin is unchanged. The default-model radio is left alone: it is a 22x20 input inside an 86x42 `<label>` that activates it, so the input's own box is not what a pointer has to hit.
- Fixed `.safe-default` being a 20px target on any machine without a CJK font installed. Its size came from padding added to a `line-height: normal` line box, and the label is Chinese, so it is a CJK fallback — not the declared font stack — that decides how tall it is. The line box is now a fixed number. CI caught this where local runs could not: a measurement only ever sees the fonts of the machine taking it, so the size being font-independent is asserted rather than measured.
- Added an aggregate `npm test` that runs the build and all nine suites in order. Each suite already had its own script and there was no single command that ran everything.
- Documented CLIProxyAPI, sub2api, and New API as prior art for the Responses translation this project deliberately does not own. `docs/compatibility.md` records what each one is worth reading for; `AGENTS.md` states that they are reference implementations rather than templates to copy in.

## 0.3.0 - 2026-08-22

- Added global prompt management for both agents. Each instruction file holds one document at a time and the alternatives live in this manager's own `0600` store, the same shape the Codex provider list already uses. Pi reads `AGENTS.md`, `SYSTEM.md`, and `APPEND_SYSTEM.md` from `~/.pi/agent`; Codex reads `AGENTS.md` from `$CODEX_HOME` — verified against Pi's own README and, for Codex, by finding the file's text in `codex debug prompt-input`. One screen serves both agents because the server declares which files each one reads, so neither is special-cased. A file that predates the manager is adopted rather than presented as absent, on the read path only, and deleting the document currently in a file requires naming its replacement.
- Prompt text is returned to the browser, unlike a credential. That is a deliberate exception, recorded in `AGENTS.md`: a document nobody can read back cannot be edited, and anything secret belongs in a credential.
- Extracted the snapshot, revision, and all-or-nothing write machinery into `lib/managed-files.mjs`. Pi, Codex, and now each agent's prompt files need exactly the same guard, and a third hand-written copy is how the invariants drift apart.

- Stopped generating `[profiles.*]` tables, and remove the ones 0.2.0 and 0.2.1 wrote. Codex 0.149.0 demoted profiles in `config.toml` to legacy and refuses `--profile <name>` outright while a matching table is present — `Error loading config.toml: --profile \`custom\` cannot be used while ... contains legacy ... [profiles.custom]` — so the manager was breaking the exact command its success screen told people to run. `codex doctor` had reported the config as fine, because a legacy table still parses; only the selector rejects it, which is why generating them survived review. Switching model within a provider is now `codex -m <model>`, plus `-c model_reasoning_effort=` when the effort differs. The next save clears the recorded tables and nothing else: a `[profiles.*]` written by hand survives even when it shares the prefix. `tests/codex-real-binary.test.mjs` now runs the advertised command against the real binary rather than only asking whether the config loads.
- Fixed the managed bridge never noticing a LiteLLM installed after the manager had started. The executable was resolved once at startup, and since the documented order is to open the manager first and install LiteLLM when you find you need it, the usual case was the broken one — with no way out, because the launcher reuses an already-running manager rather than restarting it. The path is now resolved on every read, and a newly discovered executable is probed for its version rather than inheriting the failed probe of the one that did not exist yet.
- The launcher says when it reused an instance that was already running, reports that instance's own version and config directories rather than the ones this shell computed, and gives the command to restart it. Previously a reused server printed exactly what a freshly started one printed.

## 0.2.1 - 2026-08-22

- Fixed the LiteLLM version never being reported. `litellm --version` takes eight to nine seconds — it imports a very large Python package — and the probe ran inside the status path with a three-second bound, so it always timed out and the credentials step showed nothing. That mattered: an install too old to bridge is otherwise indistinguishable from a broken upstream, and 0.2.0's own release notes told people to check that number. The probe now runs in the background and the answer appears once it lands, so no request ever waits on it and a binary that never answers costs nothing.

## 0.2.0 - 2026-08-22

- Added Codex CLI support. A Pi/Codex switch at the top of the sidebar routes the same provider list, three-step wizard, settings screen, and success handoff to whichever agent you are configuring; the Pi side is unchanged. The manager writes `$CODEX_HOME/config.toml` and `auth.json`, remembers every provider's definition and key in its own `0600` store, and switches the active gateway in one click.
- `config.toml` edits are surgical. A small TOML document model rewrites only the manager's own `[model_providers.<id>]` table, its generated `[profiles.*]`, and the top-level model keys; comments, unrelated keys, and provider tables written by hand survive byte for byte. Regenerated profiles are deleted by recorded name rather than by prefix, so a hand-written profile sharing the prefix is not swept away.
- A `config.toml` that predates the manager is adopted rather than overwritten: if the owned table matches nothing in the store, the file wins and the entry is labelled as adopted. Reading state never writes, so opening the page cannot disturb a working setup.
- The managed bridge finds LiteLLM on its own. PEP 668 pushes it into a virtualenv or under pipx and off `PATH`, so the manager looks where those installers actually put it before falling back to `PATH`, and the credentials step names the executable and version it picked. `PI_PROVIDER_MANAGER_LITELLM` is now a fallback rather than a requirement.
- Added a managed bridge for upstreams that expose only `/v1/chat/completions`, which Codex cannot reach at all since it dropped the `chat` wire protocol. Choosing that path asks for the upstream's own address and key; the manager writes LiteLLM's config, points Codex at the local proxy with `requires_openai_auth = false`, and starts and stops the process. The user installs LiteLLM and nothing else. The upstream key enters neither config file — it lives in the manager's `0600` store and reaches LiteLLM through an environment variable. The proxy is pinned to `127.0.0.1`, because LiteLLM defaults to `0.0.0.0` and would otherwise publish an unauthenticated proxy holding that key on every interface; it is started detached so closing the manager does not cut Codex off; and a recorded process id is never signalled unless procfs still shows it running the manager's own config file, since process ids are reused.
- The managed bridge degrades honestly where its ownership check cannot run. Proving a started process is still ours needs procfs, so on a platform without it — native Windows included — the manager declines to supervise, still writes LiteLLM's config, and shows the command to run by hand with the upstream key named rather than embedded. The Pi side and directly connected Codex providers are unaffected.
- This project still does not translate model traffic. Writing a third-party config file and supervising a process is the same work it already does for Pi and Codex; the translation stays LiteLLM's to maintain, which matters because the part that keeps moving is Codex's side of the wire and Codex ships weekly.
- Codex writes carry their own revision, separate from Pi's, so editing one agent's configuration cannot invalidate an in-flight draft for the other. All three Codex files move together or roll back together.
- Added `codexValidatedVersion` to `package.json` and Codex version detection to the server, shown side by side in the Codex settings screen under the same one-copy rule as `piValidatedVersion`.
- Extracted the atomic-write, validation, and TOML primitives into `lib/`, shipped as source in the release archives; both launchers now resolve and pass the Codex directory explicitly, because a detached WSL process does not inherit the calling shell's environment.
- Fixed the launcher hanging on its own port probe. `port_in_use` connected through bash's `/dev/tcp`, which has no connect timeout; under WSL2 mirrored networking a connect to an unbound loopback port never returns, so the launcher stalled on its first candidate port with nothing on screen. It now asks Node whether the port can be bound. The launcher also prints its URL and both config directories unconditionally, and detaches the browser bridge, so a blocked `wslview` or `powershell.exe` can no longer look like a hang.

- The Codex settings screen now names any hand-written `[model_providers.*]` table that omits `name`. Verified against the real binary: one such table makes Codex refuse to load the entire config, every other provider included. The manager preserves those tables rather than repairing them, so the least it can do is say which one is at fault.
- Added `npm run test:codex-real`, which runs the installed `codex` binary against manager-generated configuration and proves both paths end to end, offline and without a key. The direct path asserts Codex sent the exact credential the manager stored; the bridged path stands up a gateway that refuses `/v1/responses`, has the manager configure and start LiteLLM in front of it, and asserts `codex exec` completes a turn while the upstream sees only authenticated Chat Completions. It skips itself where Codex or LiteLLM is absent, so it is the first thing to run after a Codex upgrade.

The managed bridge was additionally exercised on the owner's WSL2 machine against a real third-party gateway: the manager generated LiteLLM's config, started the proxy, and Codex resolved the bridged model and had its request accepted.

**Validated against Codex `0.149.0`.** On 2026-08-21 a real `codex-cli 0.149.0` on WSL2 started against a manager-written `config.toml` and reported the expected model and reasoning effort, confirming the generated `[model_providers.*]` table passes its `deny_unknown_fields` check. Per-project trust tables keyed by quoted paths containing slashes and CJK, and legacy keys such as `disable_response_storage`, survived the round trip. This is now automated as `npm run test:codex-real`, which asserts `codex doctor --json` reports `config.load: ok` after the manager rewrites a realistic file; `reachability mode` also switches to `API key auth`, confirming Codex resolved the generated provider and took the `auth.json` credential path. The dated record is in `design-qa.md`; see `docs/compatibility.md` for the items to recheck on a Codex upgrade.

## 0.1.9 - 2026-08-19

- Added optimistic concurrency protection across `auth.json`, `models.json`, and `settings.json`. The server returns an opaque HMAC revision with every state response and requires it on provider, deletion, and settings writes. If CC Switch, another browser tab, or a text editor changed any managed file, the stale request returns HTTP 409 without writing; the UI keeps the draft and offers to reload.
- Added prebuilt release archives for Linux/WSL and Windows. They contain the built UI, dependency-free Node server, documentation, and platform launchers without `node_modules` or Pi data. A release-published workflow builds both archives from the tag, while CI validates the staging contents and parses the PowerShell launcher on Windows.
- Made both launchers resolve a bundled project relative to their own location, so an extracted release can run from any directory while copied launchers and the existing environment overrides continue to work.
- Moved the project into focused maintenance mode. CC Switch now owns the broader Pi workflow; this manager remains intentionally limited to Pi credentials, runtime defaults, and native-file consistency. The unstarted CC-Switch/CSV import and model-discovery roadmap is retired.

**Validated against Pi `0.84.2`.** The Pi-facing schema is unchanged from 0.1.8. Production-shaped regressions exercise successful writes, externally modified files, HTTP 409 conflicts, preserved external fields, and the browser reload action using isolated temporary Pi directories.

## 0.1.8 - 2026-08-19

- Added guarded provider deletion. A named confirmation dialog removes the provider and all of its models, deletes its stored credential by default, and can explicitly retain that credential for later reuse. Deleting Pi's current default requires a valid replacement provider/model; the server validates and writes all three files as one rollback-protected operation, so stale tabs and direct API calls cannot break the invariant.
- Persisted model IDs are now read-only storage identities. ## 0.1.4 - 2026-08-18

Security release. Upgrade if you have ever run the manager while browsing the web.

- **Fixed credential theft through cross-origin writes.** The local API accepted any POST regardless of `Origin`, `Host`, or `Content-Type`. A page the user visited could submit a `text/plain` form post — a CORS simple request, so never preflighted — and use `credential.mode: "migrate"` to copy the user's stored API key onto a provider with an attacker-controlled `baseUrl`, then mark it default. The next `pi` session would send the real key to the attacker. Requests to `/api/` now require a loopback `Host` on the service port, which also blocks DNS rebinding, and mutating requests must send `Content-Type: application/json`, which forces a preflight that is never answered.
- **Fixed silent destruction of a stored credential.** `credential.fromProvider` was unvalidated, so `__proto__`, `constructor`, and `toString` passed an existence check by resolving on `Object.prototype`, overwrote a real key with `{}`, and returned success while the UI still showed the credential as configured. Migration sources must now be an own, object-valued entry matching the provider-id pattern. The same unguarded lookup in the settings endpoint is fixed too.
- Added regression tests for cross-origin writes, DNS rebinding, prototype-chain credential sources, and the legitimate paths that must keep working.
- The dev proxy now sets `changeOrigin`, so proxied requests present the API's own host.
